# Mirrorly MVP 开发任务拆分 v1.0

> 状态：待评审 · 日期：2026-09-12
> 依据：PRD v0.2（M1–M10）、TECH_RISKS v1.0、CLI_SPEC v1.0、DESIGN_DECISIONS v1.0。
> 每个任务：输入 / 输出 / 验收标准 / 测试要求。任务按依赖顺序编号，T-01→T-10 可顺序执行。

## 依赖关系

```
T-01（仓库与配置基建）
 ├─ T-02（扫描与变更检测）
 │   └─ T-03（快照写入引擎）
 │       ├─ T-04（manifest 管理）
 │       ├─ T-05（中断恢复）
 │       ├─ T-06（完整性校验）
 │       ├─ T-07（保留策略）
 │       └─ T-08（恢复）
 └─ T-09（CLI 集成与报告）
     └─ T-10（端到端验收）
```

---

## T-01 仓库初始化与配置加载（对应 M1 基础、M10 卷标识）

- **输入**：`init` 命令参数（source/target/filesystem-policy）；TOML 配置文件。
- **输出**：目标侧 `MirrorlyRepo/` 目录结构（repo.json、snapshots/、manifests/、locks/、logs/）；本地 `config.d/<task>.toml`；配置解析模块（严格模式，未知键报错）。
- **验收标准**：
  1. NTFS 目标初始化成功，repo.json 含格式版本、卷标识（Volume GUID/序列号）、哈希算法；
  2. exFAT/FAT32 目标：`strict` 策略拒绝并提示转 NTFS；`warn` 策略输出能力限制说明，用户确认后继续并标注降级；
  3. 对已存在仓库重复 init 报错（退出码 1）；
  4. 配置含未知键时报错并指出键名。
- **测试要求**：临时目录下对三种文件系统策略分支做单元测试（卷标识可用 mock）；TOML 解析的正反例用例。

## T-02 源扫描与变更检测（M2、M6、ADR-006）

- **输入**：源目录、排除规则（glob）、上一快照 manifest。
- **输出**：变更集（新增/修改/删除/疑似修改四类列表）；文件元数据采集（大小、mtime_ns）；哈希复核模块（BLAKE3，流式分块读取）。
- **验收标准**：
  1. 空基线时全部为"新增"；
  2. 仅 mtime 变化不触发"修改"（大小+内容不变 → 哈希复核后归类不变）；
  3. 大小变化或哈希不同 → "修改"；
  4. 排除规则对文件与目录均生效（如 `node_modules/` 整树跳过）；
  5. 长路径（>260 字符）与中文/Unicode 文件名正确处理（TR-6）。
- **测试要求**：构造固定目录树的快照测试（pytest `tmp_path`）；长路径与 Unicode 用例；排除规则矩阵用例；哈希复核仅对疑似项触发（用计数断言）。

## T-03 快照写入引擎（M1、M2、M4、TR-2 不变量）

- **输入**：变更集、源目录、目标仓库、上一快照路径。
- **输出**：新快照目录树（未变文件硬链接复用、变更文件整文件写入）；写入流程遵循"临时文件 + fsync + 原子改名"。
- **验收标准**：
  1. 未变文件与上一快照共享 inode（硬链接数 >1，可用 `os.stat` 断言）；
  2. 变更文件为独立新文件，历史快照内容不受影响（核心回归：改写源文件后旧快照字节不变）；
  3. 源中已删除文件在新快照中不存在，但旧快照保留（M4）；
  4. 空目录结构保留；
  5. 复制中源文件发生变动 → 跳过该文件并在报告中记录（TR-4，退出码 3）。
- **测试要求**：inode 断言；历史快照不可变性回归测试；复制中注入变动（mock mtime 变化）的跳过用例。

## T-04 Manifest 管理（M3、ADR-010）

- **输入**：变更集执行结果、快照统计。
- **输出**：`manifests/<id>.json`（含头部与逐文件条目）；写入经 `manifests.tmp/` 原子提交；incomplete→complete 状态流转。
- **验收标准**：
  1. manifest 头部字段齐全（format_version、snapshot_id、created_at、source_root、hash_algorithm、status、统计）；
  2. 条目与实际快照目录树一致（双向核对）；
  3. 写入中途 kill 进程，不产生"半个 complete manifest"（只有 tmp 残留）；
  4. `list` 能正确解析并展示全部快照状态。
- **测试要求**：JSON schema 校验用例；kill 模拟（写 tmp 后中断）用例；10 万级条目的读写性能冒烟（记录耗时，不设硬阈值）。

## T-05 中断恢复（M7、TR-5）

- **输入**：含 incomplete manifest 的仓库、当前源目录。
- **输出**：续传完成的 complete 快照；清理 tmp 残留。
- **验收标准**：
  1. 备份中途 kill 后重跑 `backup`：检测到 incomplete，提示并以其为基线续传，不从头复制全部文件；
  2. 已完成硬链接的部分直接复用；
  3. 重复中断/重跑多次后结果与一次性完成一致（最终快照树逐字节一致、manifest status=complete）。
- **测试要求**：在不同进度点注入中断（按文件计数触发）的集成测试；多次中断用例。

## T-06 完整性校验（M5、TR-3、ADR-009）

- **输入**：快照 manifest、快照目录树。
- **输出**：`verify` 报告（逐项比对结果、总结论、退出码 0/4）；写入路径的"写入即校验"（复制后重读哈希比对，失败重试一次再报错）。
- **验收标准**：
  1. 正常仓库 verify 通过（退出码 0）；
  2. 篡改目标文件任一字节 → verify 检出并定位到文件（退出码 4）；
  3. 删除目标文件 → 检出缺失；
  4. `--quick` 模式不重算哈希；
  5. 写入即校验失败时任务报错，不标记 complete。
- **测试要求**：字节篡改/删除/权限损坏三类注入用例；quick 模式断言未读文件内容。

## T-07 保留策略（M3、ADR-008）

- **输入**：快照列表、retention 配置（keep_last、keep_monthly）。
- **输出**：过期快照目录与对应 manifest 的删除；保留集合计算结果。
- **验收标准**：
  1. 仅删除同时不满足 keep_last 与 keep_monthly 的快照；
  2. 最近 N 个快照永远保留；每月最早一个快照在 keep_monthly 期限内保留；
  3. incomplete 快照不被保留策略删除（由用户或续传处理）；
  4. dry-run 显示将删除的快照列表而不实际删除。
- **测试要求**：构造跨多月、不同密度的快照序列，断言保留集合；边界：快照数 < keep_last 时不删任何。

## T-08 恢复（restore，TR-4 防覆盖）

- **输入**：快照 id、`--to` 目录、`--path` 过滤、`--overwrite` 策略。
- **输出**：恢复出的文件树；恢复报告。
- **验收标准**：
  1. 恢复到空目录：文件树与快照逐字节一致；
  2. `--path` 只恢复匹配子树；
  3. 目标已存在同名文件：`never` 跳过、`older` 仅当目标更旧时覆盖、`always` 覆盖——三种策略行为正确且恢复前列出清单；
  4. 无 `--in-place` 时拒绝恢复到原源路径。
- **测试要求**：逐字节比对用例；三种覆盖策略矩阵；子树过滤用例。

## T-09 CLI 集成与报告（M8、M9、CLI_SPEC 全部命令）

- **输入**：CLI_SPEC v1.0。
- **输出**：`init/backup/verify/restore/list` 五命令全部可用；退出码符合规范；备份/校验报告写入 `logs/` 并终端摘要；`--dry-run`、`--json` 生效；任务锁（并发第二实例退出码 6）。
- **验收标准**：逐命令对照 CLI_SPEC 验收；退出码 0–6/130 各有触发路径；dry-run 不产生任何写入（目录树 diff 为空）。
- **测试要求**：CLI 层集成测试（`subprocess` 或 click/typer 测试 runner）覆盖每个命令的 happy path 与主要错误路径；退出码断言。

## T-10 端到端验收（外置盘场景，TR-7）

- **输入**：真实或仿真的外置盘环境。
- **输出**：端到端测试报告；已知限制清单更新到 docs。
- **验收标准**：
  1. 完整流程：init → 多次 backup（含变更与删除）→ verify → restore → 保留清理，全部通过；
  2. 盘符变化后 backup 仍能识别目标卷（卷标识匹配）；
  3. 插错盘（卷标识不符）→ 退出码 5，零写入；
  4. 10 GB 级混合数据集（含 >4 GB 大文件、万级小文件）备份耗时与空间占用记录在案（作为性能基线，不设通过阈值）。
- **测试要求**：脚本化端到端用例（可在本地 NTFS 分区仿真）；性能基线数据归档到 DEVELOPMENT_LOG。

## 规模估算与执行建议

- T-01~T-04 是骨架（约占总工作量 40%），T-05/T-06 是可靠性核心（约 30%），T-07~T-10 为完整性与验收（约 30%）。
- 建议每个任务单独提交，按 T-01→T-10 顺序推进；T-03 的"历史快照不可变性"与 T-06 的校验是每次提交后都应跑的回归防线。
- 测试框架 pytest（已在 dev 依赖）；所有涉及文件系统的测试用 `tmp_path` 隔离，不依赖外置盘（T-10 除外）。
