# Mirrorly 关键设计决策分析（存储与配置）

> 版本：v1.0 · 日期：2026-09-12
> 本文对 MVP 开发前最后三项关键选型做对比分析，结论同步落档为 ADR-010 / ADR-011 / ADR-013（见 ARCHITECTURE.md）。

---

## 1. Manifest 设计

快照元数据（文件清单：路径、大小、mtime、哈希、链接目标等）是 Mirrorly 的核心数据结构。三个候选方案：

### 方案对比

| 维度 | A. 单一 JSON 清单 | B. SQLite 数据库 | C. 每快照独立 manifest（JSON） |
| --- | --- | --- | --- |
| **可靠性** | 差：单文件持续增长，每次备份全量重写，写入中断即整个库损坏 | 较好：WAL 模式抗崩溃，但仍是单点——库损坏影响全部历史 | 好：每次备份只新增一个文件，写坏只影响当次快照，历史快照只读不动 |
| **可恢复性** | 差：损坏后全部版本信息丢失 | 中：可用 sqlite 修复工具，但门槛高 | 好：任一快照独立可恢复；极端情况下可从快照目录树重建 manifest |
| **人类可读性** | 好但体积大后不可用 | 差：二进制，需要工具 | 好：单快照 JSON 大小可控（10 万文件约 10–20 MB），可直接查看/diff |
| **未来 GUI 扩展** | 中：加载全量慢 | 好：查询灵活（按路径/时间检索） | 中：列出快照读目录即可；浏览单快照加载单文件；跨快照检索需遍历（v1 无此需求） |
| **损坏恢复** | 差：全有或全无 | 中：页级损坏可能扩散 | 好：损坏域 = 单个快照，verify 可逐快照独立校验 |
| **实现复杂度** | 低 | 中高（schema 迁移、并发锁） | 低 |
| **备份一致性** | 追加写需小心 | 好（事务） | 天然契合"快照只读不变量"（TR-2/TR-5）：先写临时文件，完成后原子改名 |

### 决策：**方案 C —— 每快照独立 JSON manifest**

- 与已确认的核心架构不变量（快照目录只读、原子提交）天然一致；
- 损坏域最小化，符合 TR-3/TR-5 的容错设计纪律；
- 人类可读、可 diff、可用普通工具检查，呼应"备份产物透明可恢复"的产品差异点（D2）；
- SQLite 的查询优势在 v1 无对应需求（无跨快照检索）；未来 GUI 若需要全局索引，可在 SQLite 中构建**可再生的派生索引**（manifest 仍是唯一事实来源）。

### 仓库布局（据此确定）

```
<target>/MirrorlyRepo/
├── repo.json                  # 仓库信息：格式版本、卷标识（M10）、创建时间、哈希算法
├── snapshots/
│   ├── 2026-09-12_220000/
│   │   ├── <镜像目录树，未变文件为硬链接>
│   │   └── ...
│   └── 2026-09-13_090000/
├── manifests/
│   ├── 2026-09-12_220000.json
│   └── 2026-09-13_090000.json
├── manifests.tmp/             # 写入中的临时区（原子改名来源）
└── locks/                     # 任务锁（TR-4）
```

manifest 与快照目录分离存放：保持快照目录为纯数据（用户可直接浏览拷贝），元数据集中管理、便于 verify/retention 操作。

### manifest JSON 结构（v1 约束）

- 头部：`format_version`、`snapshot_id`、`created_at`、`source_root`、`hash_algorithm`、`status`（`complete`/`incomplete`）、统计计数；
- 条目数组：每文件一条 `{path, size, mtime_ns, sha}`；目录单独记录（保留空目录与权限占位）；
- `incomplete` 状态支持中断恢复（TR-5）：重跑时以 incomplete manifest 为增量基线，完成后改写为 `complete`（临时文件 + 原子改名）。

## 2. 配置文件设计

### 方案对比

| 维度 | TOML | YAML | JSON |
| --- | --- | --- | --- |
| **人类手写友好** | 好：语法直白、支持注释、错误易定位 | 中：缩进敏感、隐式类型转换坑多（`no`→false、`2026-09-12`→日期） | 差：不支持注释、无尾逗号 |
| **解析依赖** | **零依赖**：Python 3.11+ 标准库 `tomllib`（读）；写可用 `tomli-w` 或模板生成 | 需第三方 `pyyaml`，且安全加载需注意 | 零依赖（stdlib `json`） |
| **多备份任务模型适配** | 好：`config.d/<task>.toml` 每任务一文件，天然支持 ADR-007 的多任务预留 | 好 | 中 |
| **GUI/工具互操作** | 好：格式严格、跨语言解析器成熟 | 好 | 最好 |
| **配置错误风险** | 低：解析失败即报错，无歧义 | 中高：合法 YAML 但语义错误的情况多 | 低 |

### 决策：**TOML**

- 配置文件由用户手写/手改（CLI 工具的常态），TOML 在可读性与严格性之间最平衡；
- 读解析零第三方依赖（`tomllib`），降低安装门槛；
- 多任务结构：`config.toml`（全局默认）+ `config.d/*.toml`（每任务一个文件）。MVP 只实现单任务，但目录约定现在确定，未来多任务无需迁移。

### 配置结构约定（v1）

```toml
# config.d/daily.toml（示例，非实现）
[task]
name = "daily"
source = "D:/Data"

[target]
path = "E:/MirrorlyRepo"        # 写入时记录卷标识，运行时校验（M10）
filesystem_policy = "strict"    # strict: 非 NTFS 拒绝；warn: 提示后由用户确认继续

[filter]
exclude = ["*.tmp", "node_modules/", "$RECYCLE.BIN/"]

[retention]
keep_last = 30
keep_monthly = 12               # 每月至少保留 1 个，最长 12 个月

[verify]
on_write = true                 # 写入即哈希校验（ADR-009）
```

未知键一律报错（严格模式），防止拼写错误静默失效。

## 3. 哈希算法选择

### 方案对比

| 维度 | SHA-256 | BLAKE3 | xxHash（XXH64/XXH3） |
| --- | --- | --- | --- |
| **性质** | 密码学安全 | 密码学安全 | **非密码学**（仅检错，不抗构造碰撞） |
| **速度（大文件，单线程量级）** | 基准：约 300–500 MB/s（无 SHA-NI 加速更慢） | 基准：约 2–4 GB/s（SIMD 并行，约为 SHA-256 的 5–10 倍） | 极快：>10 GB/s |
| **备份场景适配** | 安全但慢：TB 级全量哈希耗时数倍于 BLAKE3 | 最适合：写入即校验（ADR-009）在大文件场景不再构成瓶颈 | 不能用于完整性校验：攻击者/损坏可构造同哈希内容，TR-3 不可接受 |
| **Python 依赖** | 零依赖（`hashlib` 标准库） | 第三方包 `blake3`（有官方 Windows wheel，安装可靠） | 第三方包 `xxhash` |
| **生态/可验证性** | 最广泛，任何系统自带工具可复核 | 生态成熟，跨平台 CLI 工具可用 | 广泛但仅限非安全用途 |

### 决策：**BLAKE3 为主，SHA-256 为降级兜底；xxHash 不用于校验**

- 主哈希：**BLAKE3**——备份是"大量顺序读 + 哈希"的负载，正是 BLAKE3 的设计目标场景；写入即校验（M5）在机械硬盘外置盘上尤其需要哈希不成为瓶颈；
- 兜底：若 `blake3` 包安装失败（罕见环境），自动降级 `hashlib.sha256` 并在报告中明示——manifest 头部记录 `hash_algorithm`，同一仓库内算法不可混用（init 时锁定，verify 按记录值执行）；
- xxHash 不采用：完整性校验必须是密码学哈希（TR-3 结论）；变更检测初筛用的是元数据（ADR-006），也无 xxHash 的用武之地；
- 依赖决策：`blake3` 加入 `pyproject.toml` 主依赖（有官方 wheel，风险可控）。
