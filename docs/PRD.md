# Mirrorly 产品需求文档（PRD）v0.1

> 状态：**草案，待确认** · 版本：v0.1 · 日期：2026-09-12
> 本文档中的 ⚠️ 标记为关键假设，需产品负责人确认后转正式。

## 1. 背景与定位

### 1.1 一句话定位

**Mirrorly 是一个面向个人用户的本地版本化备份工具**：把选定的文件夹单向备份到本机或外置磁盘，保留多个历史快照，让"误删、改坏、磁盘坏"都能找回。

### 1.2 为什么是它（调研结论摘要）

- 个人数据丢失的三大主因：误删/误改、硬件故障、勒索软件。防线是**版本化备份**，而非云同步（同步会把删除和加密一并传播）。
- 业界共识 3-2-1 原则：3 份副本、2 种介质、1 份异地。Mirrorly 先解决其中的**本地/外置盘副本**，这是恢复最快、成本最低的一层。
- 现有工具的空档：restic/borg 强大但偏 CLI 极客向且存储格式不透明（恢复依赖工具本身）；FreeFileSync 面向文件夹同步、历史版本能力弱；Time Machine/File History 绑定操作系统。Mirrorly 的机会：**备份产物是普通文件 + 可读快照目录，不依赖专有格式，拔掉盘也能直接看**。

### 1.3 与"同步"的边界（关键决策 D1）

⚠️ **决策 D1（推荐）：v1 只做单向版本化备份，不做双向同步。**
- 理由：备份与同步是两类问题。双向同步的冲突合并是最难做对的部件，且同步天然不带历史版本，无法防误删/勒索。先把"绝不丢数据"做扎实，再谈多端一致。
- 代价：无法满足"两台电脑文件实时一致"的用户——v1 明确不服务该场景。
- 假设：用户的核心痛点是**数据安全（可恢复）**，而非多端一致性。调研中个人用户丢失数据的主因均指向可恢复性，支持此假设。

## 2. 目标用户画像

### P1 主力画像：技术型个人用户（开发者/数码爱好者）

- 特征：Windows 主力机 + 至少一块外置硬盘；数据在几十 GB～数 TB；命令行无障碍；重视数据可控、离线可用、不被订阅绑架。
- 场景：代码以外的个人资料（文档、照片、配置、下载库）定期备份到外置盘；换机时整机迁移。
- 期望：备份过程透明可验证，恢复不需要装同款软件。
- 注：本画像与项目所有者自身场景一致（Windows + 外置盘 P:\），v1 按其需求打磨。

### P2 次要画像：内容创作者（摄影/设计/视频）

- 特征：海量大文件（RAW、工程文件），单文件可达数 GB；按项目归档到外置盘。
- 场景：项目素材目录的定期快照；旧项目冷存储前的最终备份。
- 期望：大文件拷贝可靠、断电能续、速度快于手动复制。

### 明确不服务（v1）

- 企业/团队用户（权限、审计、集中管理均超出范围）
- 纯图形界面小白用户（v1 为 CLI，P1 画像可用；GUI 列入后续）
- 需要多设备实时同步的用户（见 D1）

## 3. MVP 范围

### 3.1 v1 必须支持（Must）

| # | 功能 | 说明 |
| --- | --- | --- |
| M1 | 单向目录备份 | 源目录 → 本地/外置盘目标目录，递归全量首次备份 |
| M2 | 增量备份 | 仅传输新增/变更文件（按大小+修改时间初筛，必要时哈希复核） |
| M3 | 版本化快照 | 每次备份生成一个快照版本，可列出/浏览/恢复任意历史版本；保留策略可配（如保留最近 N 个） |
| M4 | 删除保护 | 源中删除的文件在快照历史中仍可找回；当前版本默认保留被删文件的标记而不物理清除 |
| M5 | 排除规则 | glob 风格的包含/排除列表（默认排除常见缓存/临时目录） |
| M6 | 完整性校验 | 写入目标后按哈希校验，失败即报错不静默通过 |
| M7 | 中断恢复 | 备份中断后重跑可继续；目标端永不留半成品文件（临时文件+原子改名） |
| M8 | 备份前预览（dry-run） | 列出将复制/跳过/删除的文件及预计传输量，确认后执行 |
| M9 | 备份报告 | 每次运行输出统计与错误清单（文件数、字节数、耗时、失败项） |
| M10 | 外置盘识别 | 按卷序列号/卷标识别目标盘，盘符漂移（D:\→E:\）不导致备份写错位置 |

### 3.2 v1 明确不支持（Won't，防范围蔓延）

| # | 不做项 | 原因 |
| --- | --- | --- |
| W1 | 双向同步 / 冲突合并 | 见 D1；v2+ 再评估 |
| W2 | 云存储后端（S3/B2/WebDAV） | 需要传输/认证/限速一整套新层；MVP 聚焦本地 |
| W3 | 内容分块去重（restic 式） | 复杂度高；v1 用整文件级去重（见 D2），空间换简单 |
| W4 | 加密 / 压缩 | 与 D2 的"透明可恢复"目标冲突；备份目标默认视为可信本地盘；列入 v2+ 评估 |
| W5 | 实时文件监控自动触发 | ReadDirectoryChangesW 可靠性坑多；v1 手动触发 + 交给系统任务计划程序定时 |
| W6 | GUI / 后台常驻服务 | v1 CLI；GUI/托盘服务列后续 |
| W7 | 系统镜像 / 整机可启动备份 | 属于磁盘克隆工具领域（如 Veeam Agent），非文件级备份 |
| W8 | 多设备 P2P 同步（Syncthing 领域） | 与定位不符 |
| W9 | 移动端 / Web 端 | 无此场景 |
| W10 | 非 Windows 平台 | 见 D3；代码结构上不为跨平台设障，但不验证 |

## 4. 关键决策与推荐方案

### D1 定位：备份优先（不做同步）
见 1.3。**推荐：采纳。**

### D2 备份存储模型：整文件快照 + 硬链接去重
- **推荐方案**：每次快照是一个普通目录树（如 `snapshots/2026-09-12_220000/...`），未变更的文件与上一快照之间用**硬链接**共享存储（类 Time Machine / rsnapshot 模型），变更文件整文件重写。
- 理由：
  - 备份产物是普通文件，任何文件管理器可直接浏览/拷走，恢复零工具依赖——这是相对 restic/borg 的核心差异点；
  - NTFS 原生支持硬链接（`os.link`），实现简单；
  - 空间效率可接受：个人数据相邻版本间变更比例低，整文件级共享已能省大部分空间。
- 已知代价（⚠️ 假设可接受）：同一文件的大文件小改动会整文件重存（无块级去重）；FAT32/exFAT 外置盘不支持硬链接——M10 需在初始化时检测目标文件系统，exFAT 则降级为"整文件复制+软删除标记"或明确提示改用 NTFS。
- 备选（未选）：restic 式内容寻址分块库。去重/加密强，但格式专有、实现复杂度数倍、与"透明可恢复"冲突。

### D3 平台：Windows 优先
- **推荐：v1 仅验证 Windows 10/11（NTFS 主场景）。**
- 理由：项目所有者环境为 Windows；文件锁定、路径长度、大小写、ADS 等坑集中在单平台可控。代码层面用 pathlib 保持移植可能，但不做跨平台承诺。

### D4 形态：CLI 优先
- **推荐：v1 为命令行工具**（`mirrorly backup/status/restore/verify` 子命令），定时交给 Windows 任务计划程序。
- 理由：与 P1 画像匹配；可测试、可脚本化；GUI 是纯粹的增量层，后期可叠加而不动核心。

### D5 变更检测：元数据初筛 + 哈希复核
- **推荐**：以（路径、大小、mtime）建立清单对比；大小或 mtime 变化的文件进入哈希复核再决定是否重传。v1 不引入实时文件系统事件。
- 理由：全量哈希扫描对 TB 级数据太慢；纯 mtime 有极少数"内容变了时间没变"的边缘情况，故对疑似项哈希兜底。⚠️ 假设：用户对全量哈希校验无硬性要求（如需，可加 `--strict` 模式作为后续增强）。

### D6 恢复方式：直接拷贝 + 工具辅助
- **推荐**：恢复 = 从某快照目录直接复制（文件管理器即可），CLI 提供 `restore` 命令做整快照或单文件恢复、路径冲突保护。

### D7 完整性：写入后校验 + 按需全库校验
- **推荐**：每个文件复制后立即对目标端哈希校验；另提供 `verify` 命令对整个快照做抽检/全检。
- 理由：外置盘静默损坏（bit rot）是真实风险；写入即校验成本最低。

## 5. 用户故事（v1 验收视角）

- US-1（P1）作为开发者，我插上外置盘后运行一条命令，把文档库增量备份到盘上，能预览将发生什么，结束后看到报告。
- US-2（P1）我误删了上周的合同文件，能从历史快照中把它单独找回来，不需要恢复整个目录。
- US-3（P1）外置盘这次被识别成了另一个盘符，备份仍能正确写到同一块盘的目标位置，不会新建一个错位置。
- US-4（P2）备份几 TB 素材时中途断电/拔盘，重新运行后能继续，目标端没有损坏的半成品文件。
- US-5（P2）单个 8GB 视频工程文件备份成功，且完成后被告知校验通过。
- US-6（P1）我能配置排除规则，让 node_modules、浏览器缓存等目录不参与备份。
- US-7（P1）我能随时运行校验命令，确认某个历史快照的数据没有静默损坏。

## 6. 核心使用流程

```
首次配置          日常备份                 恢复
    │                │                      │
init  ──► 记录源/目标/排除规则    backup --dry-run 预览    list 查看快照
    │                │                      │
    ▼                ▼                      ▼
写入配置        backup 执行增量快照      restore <快照> [路径]
(目标盘登记卷标识)   报告 + 校验            单文件或整目录恢复到指定位置
```

## 7. 产品风险点

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| R1 外置盘为 exFAT（无硬链接） | D2 模型失效 | 初始化检测文件系统并提示；提供降级策略（⚠️ 待确认：提示拒绝 or 自动降级） |
| R2 快照目录被用户手动改动/删除 | 历史链损坏 | `verify` 可检测；文档强调快照区只读约定 |
| R3 mtime 边缘情况漏检变更 | 个别文件漏备 | D5 哈希复核兜底 + 后续 `--strict` 全哈希模式 |
| R4 源端文件被占用（锁定） | 备份失败或读出不一致 | 失败文件列入报告，不中断整体；后续评估 VSS 卷影复制 |
| R5 用户把同步误解为备份（误删后快照也"更新"掉） | 数据丢失认知偏差 | 快照只增不改的模型天然规避；文档强调 |
| R6 备份目标盘空间耗尽 | 备份中断 | 备份前预估所需空间（M8 统计），不足时提前报错 |
| R7 范围蔓延（同步/云/加密诱惑） | MVP 延期 | 3.2 明确 Won't 清单，变更需走 PRD 修订 |
