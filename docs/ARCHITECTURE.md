# Mirrorly 架构决策记录（ADR）

> 记录影响项目长期形态的技术决策。每条决策包含：背景、决定、理由、备选方案。
> ADR-001~004 为工程决策，ADR-005~009 为产品架构决策（PRD v0.2 确认），ADR-010~013 为 MVP 前最终细化决策。

## ADR-001：开发语言与运行时

- **决定**：Python 3.12，Conda 独立环境管理（环境名 `mirrorly`，位于本机默认 Conda 环境目录）。
- **理由**：备份/同步工具涉及大量文件系统操作、哈希计算与并发 IO，Python 生态（pathlib、hashlib、watchdog 等）成熟；3.12 兼容性稳定。Conda 环境与系统 Python、宿主沙箱隔离。
- **备选**：系统 Python 3.13（与工具链耦合，弃用）；Rust/Go（性能更优但迭代成本高，个人项目阶段不宜）。

## ADR-002：项目布局

- **决定**：src-layout（`src/mirrorly/`）+ `tests/` + `docs/` + `scripts/`。
- **理由**：防止测试误导入仓库根目录包；业界长期维护项目的通行做法。

## ADR-003：构建与打包

- **决定**：setuptools + pyproject.toml，`mirrorly` CLI 入口预留，dev 依赖 pytest + ruff。
- **理由**：标准、无额外学习成本；`pip install -e ".[dev]"` 即可开发。

## ADR-004：版本控制规范

- **决定**：Git，main 分支；文本统一 LF（`.gitattributes`）；备份产物目录一律不入库。
- **理由**：Mirrorly 本身是备份工具，其仓库绝不能反向成为备份存储；换行符统一避免 Windows/Linux 混合环境下 diff 噪音。

## ADR-005：备份存储模型（产品级，2026-09-12 确认）

- **决定**：单向版本化备份。每次快照为一个普通目录树；未变更文件与上一快照间用 NTFS 硬链接共享存储；变更文件整文件重写。NTFS 为 v1 正式支持的目标文件系统；exFAT/FAT32 目标不静默降级——明确提示能力限制，由用户选择继续（整文件复制模式）或转换 NTFS。
- **理由**：备份产物透明可读、恢复零工具依赖（相对 restic/borg 的核心差异）；NTFS 原生硬链接实现简单；个人数据相邻版本变更比例低，整文件级去重空间效率可接受。
- **不变量**：已完成的快照永不修改；变更文件写入新临时文件后原子替换，绝不原地写已链接文件。
- **备选**：restic 式内容寻址分块（去重/加密强，但格式专有、复杂度高，否决）。

## ADR-006：变更检测策略（2026-09-12 确认）

- **决定**：清单记录（路径、大小、mtime、哈希）；大小或 mtime 变化的文件经哈希复核后判定变更；其余信任元数据。v1 不做实时文件系统监控，不做重命名识别优化（按删除+新增处理）。
- **理由**：全量哈希对 TB 级数据不可行；疑似项哈希兜底覆盖 mtime 边缘情况；重命名在硬链接模型下代价仅一次拷贝。
- **后续增强**：`--strict` 全哈希模式。

## ADR-007：任务模型——多任务架构预留、MVP 单任务实现（2026-09-12 确认）

- **决定**：配置与内部数据模型按"备份任务（source → target + 规则）"实体设计，但 MVP 的 CLI 流程按单任务实现；任务级 lockfile 防并发。
- **理由**：避免为未验证的需求提前做多任务调度/冲突编排，同时不让单任务假设渗入数据模型，防止后期返工。

## ADR-008：快照保留策略（2026-09-12 确认）

- **决定**：保留策略配置化；默认保留最近 30 个快照，且每月至少保留 1 个。清理只删除完整旧快照，不触碰 incomplete 之外的数据。
- **理由**：控制硬链接数（NTFS 上限 1024）与磁盘占用；月度锚点保证长期可回溯。

## ADR-009：数据完整性机制（2026-09-12 确认）

- **决定**：每个文件复制后立即对目标端重算哈希与源端比对；清单持久化每文件哈希（含算法名）；提供 `verify` 命令对快照做全检。哈希算法由 ADR-013 最终确定为 BLAKE3（SHA-256 兜底）。
- **理由**：外置盘静默损坏（bit rot）与 USB 链路错误是真实风险；写入即校验成本最低、发现最早。

## ADR-010：Manifest 存储——每快照独立 JSON 文件（2026-09-12）

- **决定**：每个快照对应 `manifests/<snapshot_id>.json` 一个独立清单（头部含 format_version/status/hash_algorithm 等，条目含路径/大小/mtime_ns/哈希）；写入经 `manifests.tmp/` 临时区原子提交，状态从 `incomplete` 流转为 `complete`。仓库级信息（格式版本、卷标识、哈希算法）存 `repo.json`。manifest 与快照数据目录分离存放。
- **理由**：损坏域最小（单个快照），与"快照只读 + 原子提交"不变量天然一致；人类可读可 diff，呼应透明可恢复的产品差异点；单一 JSON 全量重写有中断损坏风险，SQLite 是单点且不可读，均否决。
- **备选**：单一 JSON 清单（否决：全量重写风险）；SQLite（否决：单点损坏、二进制不可读；未来 GUI 如需全局索引，可建可再生的派生索引，manifest 仍是唯一事实来源）。
- **详见**：docs/DESIGN_DECISIONS.md 第 1 节。

## ADR-011：配置格式——TOML，多任务目录约定（2026-09-12）

- **决定**：配置文件采用 TOML（`tomllib` 标准库解析，零依赖）；结构为 `config.toml`（全局默认）+ `config.d/<task>.toml`（每任务一文件）；解析严格模式，未知键报错。MVP 只实现单任务，目录约定现在确定。
- **理由**：用户手写场景下可读性与严格性最平衡；YAML 缩进/隐式类型坑多，JSON 不支持注释；`config.d/` 约定让 ADR-007 的多任务扩展无需迁移。
- **详见**：docs/DESIGN_DECISIONS.md 第 2 节。

## ADR-012：CLI 命令集与退出码（2026-09-12）

- **决定**：v1 命令集为 `init / backup / verify / restore / list` 五个；退出码 0 成功、1 一般错误、2 用法错误、3 部分完成（有跳过）、4 校验失败、5 目标身份不符、6 用户中止/锁占用、130 Ctrl+C。
- **理由**：命令面保持最小（不设 sync/mount/守护类命令）；退出码 0/3 区分"干净完成"与"有跳过"，使计划任务可正确告警。
- **详见**：docs/CLI_SPEC.md（契约文档，实现以其为准）。

## ADR-013：哈希算法——BLAKE3 主用，SHA-256 兜底（2026-09-12）

- **决定**：完整性哈希使用 BLAKE3（第三方包 `blake3`，有官方 Windows wheel）；`blake3` 不可用时降级 SHA-256（hashlib 标准库）并在报告中明示。算法在 init 时锁定写入 repo.json，同一仓库内不混用。xxHash 不用于完整性校验（非密码学哈希，不抗构造碰撞）。
- **理由**：备份是大文件顺序读+哈希负载，BLAKE3 约 2–4 GB/s，为 SHA-256 的 5–10 倍，保证"写入即校验"（ADR-009）在外置机械盘上不成瓶颈；SHA-256 兜底保证零第三方依赖可运行。
- **详见**：docs/DESIGN_DECISIONS.md 第 3 节。
